### تمرین عملی (روی یک کار واقعی)

**مثال واقعی:** در پروژه‌ی `mysite` اپلیکیشن «فروشگاه کتاب» (shop) را داریم. در این تمرین می‌خواهیم مسیرهای وب‌سایت را تعریف کنیم: صفحه‌ی اصلی، لیست کتاب‌ها، جزئیات هر کتاب و صفحات خطا. هدف این است که بفهمیم Django چطور آدرس درخواستی مرورگر را با الگوهای `urlpatterns` مقایسه می‌کند، ویو مناسب را پیدا می‌کند و چه زمانی یک خطای 404 می‌فرستد.

**تیتر کارها و توضیح هر کدام در این مثال:**

1. **شناخت URLconf و فایل `urls.py`**  
   هر پروژه‌ی Django یک ماژول به نام `urls.py` دارد (در ما `mysite/urls.py`). به این ماژول URLconf گفته می‌شود. قلب آن لیست `urlpatterns` است؛ لیستی از الگوهایی که می‌گویند «اگر آدرس درخواستی با این الگو هم‌خوانی داشت، این ویو را صدا بزن». فایل پیش‌فرض ابتدا مسیر پنل ادمین را دارد:
   ```python
   from django.contrib import admin
   from django.urls import path

   urlpatterns = [
       path('admin/', admin.site.urls),
   ]
   ```

2. **درک چگونگی تطبیق آدرس با الگو**  
   Django بعد از دریافت هر درخواست، قسمت مسیر (path) آن را جدا می‌کند؛ مثلاً برای آدرس `http://127.0.0.1:8000/admin/login/` مسیر `/admin/login/` است. سپس این مسیر را با الگوهای `urlpatterns` از بالا به پایین مقایسه می‌کند. اولین الگویی که با مسیر تطبیق پیدا کند برنده است و بقیه نادیده گرفته می‌شوند. به همین دلیل ترتیب تعریف الگوها اهمیت زیادی دارد.

3. **ساخت اولین ویو و تعریف اولین مسیر با `path()`**  
   در `shop/views.py` یک تابع ساده می‌سازیم:
   ```python
   from django.http import HttpResponse

   def index(request):
       return HttpResponse('فروشگاه کتاب')
   ```
   و در `mysite/urls.py` آن را به مسیر ریشه وصل می‌کنیم:
   ```python
   from shop import views

   urlpatterns = [
       path('admin/', admin.site.urls),
       path('', views.index),
   ]
   ```
   حالا با رفتن به `http://127.0.0.1:8000/` متن «فروشگاه کتاب» را می‌بینیم. اولین پارامتر `path()` الگوی مسیر، و دومین پارامتر ویوی متناظر است.

4. **اتصال urls اپلیکیشن به urls پروژه با `include()`**  
   بهتر است همه‌ی مسیرهای مرتبط با فروشگاه در خودِ اپ `shop` تعریف شوند، نه در فایل اصلی پروژه. اول فایل `shop/urls.py` را می‌سازیم و بعد در `mysite/urls.py` آن را include می‌کنیم:
   ```python
   from django.urls import path, include

   urlpatterns = [
       path('admin/', admin.site.urls),
       path('shop/', include('shop.urls')),
   ]
   ```
   حالا هر مسیری که در داخل `shop/urls.py` با `''` شروع شود، عملاً به‌صورت `/shop/...` در دسترس خواهد بود. این کار اپلیکیشن را مستقل و قابل استفاده در پروژه‌های دیگر می‌کند.

5. **آغاز `shop/urls.py` با دو مسیر ساده**  
   در `shop/urls.py` ویوها را import و مسیرهایشان را تعریف می‌کنیم:
   ```python
   from django.urls import path
   from . import views

   urlpatterns = [
       path('', views.index, name='shop_index'),
       path('books/', views.book_list, name='book_list'),
   ]
   ```
   وقتی به `http://127.0.0.1:8000/shop/books/` برویم، Django اول `shop/` را به `include` می‌دهد و بعد رشته‌ی باقی‌مانده (یعنی `books/`) را با الگوهای `shop/urls.py` مقایسه می‌کند. به این می‌گویند «حذف پیشوند»: بخشی از مسیر که در include مصرف شده، به urls داخلی نمی‌رسد.

6. **ساخت ویو `book_list` برای لیست کتاب‌ها**  
   ویوی لیست کتاب‌ها را می‌نویسیم تا مسیر `books/` یک پاسخ واقعی برگرداند:
   ```python
   def book_list(request):
       books = Book.objects.all()
       return render(request, 'shop/book_list.html', {'books': books})
   ```
   حالا می‌بینیم که مسیر کار را به ویو می‌دهد و ویو مسئول تولید پاسخ است؛ مسیریابی و منطق نمایش از هم جدا شدند.

7. **تعریف مسیر پارامتری برای جزئیات کتاب با `<int:pk>`**  
   برای صفحه‌ی جزئیات هر کتاب به یک «پارامتر» در مسیر نیاز داریم تا مشخص کند کدام کتاب را نشان بدهیم:
   ```python
   path('books/<int:pk>/', views.book_detail, name='book_detail'),
   ```
   با `<int:pk>` یک مسیر با «جای‌گذار» (converter) تعریف کرده‌ایم. Django مقدار `pk` را از داخل مسیر جدا می‌کند، مطمئن می‌شود عدد صحیح است و آن را به‌عنوان پارامتر به ویو پاس می‌دهد. آدرس‌هایی مثل `/shop/books/3/` حالا کتاب با شناسه‌ی ۳ را نشان می‌دهند.

8. **دریافت پارامتر در ویو `book_detail`**  
   تابع ویو باید پارامتر را با همان نامی که در الگو تعریف کردیم بگیرد:
   ```python
   def book_detail(request, pk):
       book = get_object_or_404(Book, pk=pk)
       return render(request, 'shop/book_detail.html', {'book': book})
   ```
   دقت کنید که نام پارامتر در الگو (`pk`) و در امضای تابع باید یکی باشد؛ وگرنه Django خطای `TypeError` می‌دهد.

9. **نام‌گذاری مسیرها با `name=`**  
   هر `path()` را می‌توان با یک نام برچسب‌گذاری کرد: `path('books/', views.book_list, name='book_list')`. فایده‌اش این است که اگر بعداً آدرس تغییر کند، لازم نیست همه‌ی لینک‌های پروژه را عوض کنیم؛ در ویوها با `redirect('book_list')` و در تمپلیت‌ها با `{% url 'book_list' %}` فقط به نام اشاره می‌کنیم. (جزئیات کامل در سرفصل «Reverse URL Lookup» می‌آید.)

10. **استفاده از پیشوند مشترک و includeهای کوچک‌تر**  
    گاهی چندین بخش سایت یک پیشوند مشترک دارند. مثلاً همه‌ی صفحات مرتبط با «مشتری» را می‌توان زیر یک `path('customer/', include('shop.customer_urls'))` گذاشت. با این تکنیک، مسیرهای هر بخش در فایل جداگانه‌ای می‌نشینند و `urlpatterns` اصلی تمیز می‌ماند — یعنی همان کاری که برای کل اپ با `include` انجام دادیم، در مقیاس کوچک‌تر هم تکرار می‌شود.

11. **خطای 404 با `get_object_or_404`**  
    وقتی کسی آدرس یک کتابِ ناموجود (مثلاً `/shop/books/999/`) را باز کند، Django باید خطای 404 بدهد. ساده‌ترین راه استفاده از `get_object_or_404` است که اگر شیء پیدا نشود، خودش `Http404` را raise می‌کند و صفحه‌ی خطا نمایش داده می‌شود. این رفتار به‌جای پیام‌های مبهم، برای کاربر معنادار است.

12. **صفحه‌ی 404 سفارشی برای سایت**  
    برای اینکه صفحه‌ی 404 ظاهر خودمان را داشته باشد، در `mysite/views.py` یک تابع می‌سازیم:
    ```python
    def my_404(request, exception):
        return render(request, '404.html', status=404)
    ```
    و در `mysite/urls.py` آن را به متغیر `handler404` وصل می‌کنیم: `handler404 = 'mysite.views.my_404'`. حالا هر خطای «پیدا نشد» در کل سایت با تمپلیت `404.html` نمایش داده می‌شود.

13. **نکته‌ی ترتیب: مسیرهای ثابت را قبل از پارامتری بنویسید**  
    فرض کنید هم `path('books/new/', ...)` و هم `path('books/<int:pk>/', ...)` داریم. الگوها از بالا به پایین بررسی می‌شوند. با `<int:pk>` درخواست `books/new/` رد می‌شود چون `new` عدد نیست و converter نوع داده را چک می‌کند؛ اما اگر جای‌نگه‌دار از نوع `<str:...>` بود، `new` پذیرفته و ویوی اشتباه صدا زده می‌شد. پس قاعده‌ی طلایی: مسیرهای ثابت را همیشه بالای مسیرهای پارامتری بنویسید.

14. **تست مسیرها در مرورگر و بررسی رفتار**  
    سرور را اجرا می‌کنیم (`python manage.py runserver`) و این آدرس‌ها را به ترتیب تست می‌کنیم:
    - `/` → صفحه‌ی اصلی فروشگاه
    - `/shop/books/` → لیست کتاب‌ها
    - `/shop/books/1/` → جزئیات کتاب ۱
    - `/shop/books/999/` → صفحه‌ی 404
    - `/shop/xyz/` → صفحه‌ی 404 (چون هیچ الگویی با آن تطبیق نمی‌یابد)
    
    این آزمایش نشان می‌دهد URLconf دقیقاً چطور درخواست را به مسیرها توزیع می‌کند.

15. **تمرین تکمیلی: طراحی مسیرهای باقی‌مانده‌ی فروشگاه**  
    برای درک کامل مطلب، مسیرهای زیر را با ترکیب مناسبی از `path()`، نام‌گذاری و `include` اضافه کنید: «تماس با ما» (`shop/contact/`)، «درباره ما» (`shop/about/`)، لیست نویسندگان (`shop/authors/`) و جزئیات یک نویسنده (`shop/authors/<int:author_id>/`). بعد از هر تعریف مسیر، یک ویوی placeholder ساده بسازید و آن را در مرورگر تست کنید.
